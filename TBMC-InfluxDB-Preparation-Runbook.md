# TBMC InfluxDB continuation runbook

This is a reusable preparation runbook, not a record of completed changes. Read the readiness report first.

1. Start an elevated commissioning session on `tp-cloud-ign02-` and confirm `10.1.0.132`. Read applicable AGENTS.md and protected deployment reports before editing. Inspect the existing service wrapper, configuration, environment, secret-store format, data paths and deployment instructions. Do not print credentials or capture secret-bearing output in transcripts. Confirm version allowing the `v2.8.0` prefix. Preserve initialization.
2. Record organization/bucket names and IDs, retention and integration authorization definitions through authenticated local APIs using credentials loaded directly from the established secret store. Keep secrets out of command arguments, console output and reports. If initialized settings differ, record and preserve them. Never reinstall or reset.
3. Obtain the gateway-observed source address and approved private path from the on-premises assessment. Confirm Ignition version, Kymera module version and bundled configuration instructions on the real gateway. Do not infer installed versions from public release listings.
4. Back up the actual service configuration and wrapper settings into an ACL-protected local directory before any edit. Preserve existing ACLs, service account and failure recovery settings. Record exact original binding and restore procedure. Avoid backing up live database files by simple filesystem copy.
5. Implement the documented private endpoint using an appropriate specific private interface or the established approved TLS proxy. Preserve local administration. If the existing service cannot bind both loopback and the required private interface, assess the documented proxy design rather than binding all interfaces blindly. Use established HTTPS and trust chains where required; do not invent a hostname or bypass certificate checks. Do not transmit credentials over public plaintext HTTP.
6. Create or adjust only the relevant inbound rule with the confirmed source IP, specific local endpoint IP, protocol and port. Account for the observed Public interface profile without changing that profile arbitrarily. Preserve unrelated rules. Do not change cloud routes, security groups or DNS without applicable authorization. Restart only if required; verify service identity, recovery settings and local health afterward. If health fails, restore the exact protected configuration backup and prior binding; reverse only the firewall change made during this continuation and verify restored health.
7. Reuse a securely retrievable dedicated token only if its status, organization and exact read/write production bucket scope are correct. Otherwise create a clearly named authorization using POST /api/v2/authorizations with actual orgID and two permissions: action read and action write, each resource type buckets, actual bucket id and orgID. Preserve unrelated authorizations. Store the result directly in the protected authoritative secret store; never print or log the response token. Review the actual module before deciding whether separate read and write tokens are supported.
8. For synthetic validation, create a uniquely named temporary bucket in the actual organization with short retention and a separate token scoped exclusively to that bucket. Write a single distinctive test point through POST /api/v2/write?org=<orgID>&bucket=<temporaryBucketID>&precision=s using that temporary token; require HTTP 204. Query that temporary bucket with POST /api/v2/query?org=<orgID>, Content-Type application/vnd.flux, Accept application/csv, using from(bucket: "<temporaryBucketName>") |> range(start: -15m) and a filter for the exact validation measurement; verify the returned value. In a finally cleanup path revoke only the temporary authorization and delete only the temporary bucket, recording cleanup failures. Do not write synthetic points into TBMC-Sensor-Data. Check the production authorization's exact permissions and perform a nonmutating authorized query; empty results alone do not verify ingestion.
9. Recheck actual Desktop resolution and synchronization before handoff. Existing restricted directory: C:\Users\tpignclouduser\Desktop\TBMC-InfluxDB-Handoff. Before secrets, verify inheritance disabled and access limited to current user, SYSTEM and Administrators. If synchronized, use a restricted nonsynchronized local folder and a Desktop shortcut. Create Ignition-InfluxDB-Connection-TEMP.txt with all fields listed in the commissioning document. Read back ACLs without printing file contents. Keep administrator credentials separate. Update the sanitized readiness report with actual IDs, retention, scopes, endpoint, source restriction, timestamps and handoff path.
10. From the actual on-premises Ignition host run Test-NetConnection against the approved destination and port, then GET <approvedURL>/health with normal certificate validation. Confirm the server-observed source matches the rule. Use the dedicated integration token from protected storage for an authenticated production bucket query. Never place the token in shell history or paste it into reports.
11. Configure the installed Kymera historian connection in the real Ignition gateway with its matching documentation, approved endpoint, actual organization/bucket and dedicated token. Verify gateway-originated historian ingestion using real authorized tag activity, then retrieve the same historical interval through Ignition and confirm timestamps, values and quality. Check store-and-forward errors. Record actual gateway/module versions and evidence. Remote synthetic tests, if needed, must target the disposable validation bucket rather than production history.
12. After secure transfer and successful actual Ignition validation, have the user confirm handoff completion, then delete the temporary plaintext copy. Retain the authoritative protected credential. Update the report with validation and deletion status, without token values.

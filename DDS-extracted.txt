
PURPOSE 目的
The purpose of this Design Specification (DS) is to provide the technical details on how (the Ignition Equipment Monitoring System) will be designed.

SCOPE 範圍

This document pertains to the software design for the SCADA-based Ignition Equipment Monitoring System, including centralized equipment monitoring, batch workflow/status management, data historization, reporting, security, and audit trail functionality.
The system scope includes the following functionality:
SCADA software platform configuration, including Ignition gateway architecture.
Data acquisition from in-scope laboratory equipment via OPC DA/UA and vendor-provided interfaces.
Centralized data historization and time-series data storage.
Relational SQL data storage for batch setup, runtime batch status, equipment selection, equipment claims, batch control audit records, and reporting support data.
User interface design principles and navigation structure.
Data visualization, trending, and batch-level reporting framework.
Batch setup functionality for saving and updating reusable batch/report configurations.
Runtime batch workflow functionality for loading saved batch setups into uniquely identifiable batch run instances/cards.
Batch status management, including statuses and actions such as Loaded, Start, Hold, Abort, Complete, and Archive, as defined by approved workflow requirements.
Equipment availability and equipment claim management for selected batch equipment.
Report selection and report generation that distinguish between multiple executions of the same saved batch name.
System security, authentication, authorization, and audit trail functionality.
Integration with on-premises IT infrastructure and cloud-based data services.
Support for alarm handling, event logging, and system monitoring as defined by project scope.
The Ignition application may write to Ignition batch/status/reporting tags and relational SQL records required to manage batch workflow state, equipment claims, audit trail records, and reporting data.
The system does not directly command, start, stop, manipulate, or otherwise control physical process equipment. No closed-loop control or direct manipulation of process equipment is included unless explicitly defined, approved, and implemented under a future formal scope change.
This SDS is developed based on and aligned with the approved Basis of Design (BOD), approved User Requirements, Functional Requirements, and formally authorized change orders. Items not explicitly described herein are considered out of scope unless covered by referenced documents or approved through formal change management.














 GENERAL DESCRIPTION
The Equipment Monitoring System is a SCADA-based platform designed to provide centralized visibility of laboratory equipment performance, process parameters, and batch-related data across multiple laboratory suites within the TBMC facility. The system is intended to improve data accessibility, reduce manual data handling, and establish a scalable and robust foundation for future advanced analytics and batch process integration.

SYSTEM OVERVIEW
The system architecture consists of an on?premises SCADA environment integrated with a secure cloud-based historian and reporting infrastructure. Process and equipment data are collected from vendor-provided equipment controllers and analyzers, aggregated through an Ignition gateway, and transmitted for storage and long-term analysis.
Key system objectives include:
Real-time monitoring of critical process parameters (CPPs)
Centralized data historization and time-series storage
Generation of batch-level and equipment-level reports
Secure access to data through role-based authentication
Scalable and modular architecture to support future expansion

 In-Scope Equipment And Areas
The system monitors lab-scale equipment located in multiple rooms and functional groups, including but not limited to:
Bioreactors and fermentation systems
Chromatography systems
Tangential flow filtration (TFF) systems
Process analyzers and sensors

Equipment connectivity and data availability vary by vendor and system type and are addressed using industry-standard communication protocols where available.

Software And Data Architecture
The SCADA platform is based on the Ignition software ecosystem and includes:
An on-premises Ignition gateway for data acquisition, visualization, and operator access
OPC UA communications to vendor equipment and controllers

A cloud-hosted time-series database for high-performance data storage and analytics
Web-based client access using browser-based interfaces

Data integrity, availability, and traceability are foundational design principles of the system. Where applicable, system functions are designed to support audit trails, controlled access, and retention of electronic records consistent with regulatory expectations.

This SDS reflects a detailed design stage following approval of the BOD and defines how the proposed system will be implemented from a software perspective. Further refinements, detailed tag definitions, alarm configurations, and report content will be finalized during implementation in accordance with approved change control procedures. 

The system will reside within a self-contained rack mounted server located on the premises of TBMC.

Data will be collected via serial gateways and hardwired digital and analog signals to the Sartorius MFCS servers. Data will be fed to the Ignition Gateway Server via OPC UA protocol.

A runtime workflow status used to identify whether a selected equipment item is loaded, officially claimed, or released for batch workflow/reporting purposes.

CLAIMED
Equipment claim state indicating that the equipment has been officially acquired by the first runtime batch instance to start. CLAIMED equipment shall be treated as unavailable to other runtime batch instances until released.
RELEASED
Equipment claim state indicating that equipment is available for use by another runtime batch instance. Equipment shall transition to RELEASED on Complete, Abort, or Archive, as defined by the batch workflow.

BATCH RUNTIME WORKFLOW 

The Batch Runtime Workflow requirements shall be maintained as the governing specification section for runtime batch behavior. User-facing screen descriptions are provided in Section 9. Security permissions and audit trail requirements are provided in Section 11.

This section defines the runtime behavior for saved batch setup records, runtime batch instances/cards, equipment availability and claims, archive behavior, reporting by Run Instance, and equipment source consistency.





Saved Batch Setup vs. Runtime Batch Instance

A saved batch setup represents a reusable batch/report configuration stored in SQL. A saved batch setup shall be identified by a unique batch_uid.

A saved batch setup may include, at minimum:
Batch name
Batch suite
Selected equipment
Batch age or report duration
Report configuration
Related setup metadata
Loading a saved batch setup shall create a new runtime batch instance/card. Each Load action shall generate a unique batch_run_uid and a Displayed Run Instance ID.

The same saved batch setup may be loaded multiple times. Each loaded/runtime batch instance shall remain uniquely identifiable in the Ignition user interface, audit trail, relational SQL records, and generated Batch Reports.

When the Setup popup is opened from a runtime batch card, the system shall use the selected runtime batch UDT path to identify and read the applicable runtime batch instance values. Runtime values shall take precedence over saved setup records where runtime tags are available. Saved setup records may be used as fallback data only where approved runtime tags are not available.





Reports and audit records shall not rely on batch name alone to identify a batch execution. Where multiple executions of the same saved batch name exist, the Run Instance and/or Displayed Run Instance ID shall distinguish one execution from another.
Equipment Availability / Claims Workflow
The Batch Runtime Workflow shall include equipment availability and equipment claim management to identify and prevent conflicting use of the same equipment by multiple runtime batch instances.
Equipment selected for a saved batch setup or loaded runtime batch instance shall be tracked using relational SQL records, including the batch_equipment_claims table or an equivalent approved schema object.
Equipment availability shall be evaluated during batch Load and Start actions. The workflow shall distinguish between equipment that has been selected for a loaded batch and equipment that has been officially acquired by a started batch.
Equipment availability and equipment claim records shall reference equipment sourced from the approved Ignition tag browser structure, including the configured equipment path, equipment name, suite, room, area, and enabled status where applicable.
The user interface shall visually indicate equipment that is already associated with a loaded, running, or otherwise active runtime batch instance. Equipment that has been selected, used, or claimed by a runtime batch instance shall be highlighted in green on the batch card or equipment selection display, or by an equivalent approved display treatment.

 Equipment Claim States

Claim State
Definition
Expected Behavior
LOADED
Equipment was selected for a loaded runtime batch instance/card.
The equipment is associated with the loaded batch but has not yet been officially acquired by a started batch. The equipment shall be visually indicated as associated with the loaded runtime batch instance.
CLAIMED
Equipment has been officially acquired by the first runtime batch instance to start.
CLAIMED equipment shall be treated as unavailable to other runtime batch instances. A runtime batch instance shall not be allowed to start with equipment that is already CLAIMED by another active runtime batch instance.
RELEASED
Equipment has been released from the runtime batch instance.
Equipment shall transition to RELEASED on Complete, Abort, or Archive. RELEASED equipment shall be available for future selection, loading, or claiming, subject to equipment enabled status and approved workflow rules.


Load and Start Behavior

When a user loads a saved batch setup, the system shall create a new runtime batch instance/card and evaluate the selected equipment against current equipment availability records.

Equipment selected for the loaded runtime batch instance shall be written to the equipment claim workflow as LOADED unless the equipment is unavailable according to approved workflow rules.

When a user starts a runtime batch instance, the system shall attempt to officially acquire the selected equipment for that batch.

The first runtime batch instance to successfully Start with available selected equipment shall transition the applicable equipment claim records to CLAIMED.

If required equipment is already CLAIMED by another active runtime batch instance, the Start control shall be disabled or the Start action shall be rejected unless an approved exception workflow is defined.

The system shall not silently overwrite, replace, or release equipment claims assigned to another runtime batch instance.

Release Behavior
Equipment claims shall be released when the associated runtime batch instance reaches a terminal or inactive workflow state.
Equipment shall transition to RELEASED when one of the following actions occurs:
Complete
Abort
Archive
On Complete, Abort, or Archive, the system shall update the applicable equipment claim records to RELEASED.

The release event shall be recorded in the batch control audit trail in accordance with Section 11. 
Archive-related equipment release shall follow the requirements defined in Section 10.3.


       10.2.4Locked Batch Behavior
When a runtime batch instance is locked due to equipment conflict or equipment ownership by another active runtime batch instance, the system shall prevent actions that would create or modify an invalid runtime control state.
For locked runtime batch instances:
START shall be disabled, blocked, or rejected.
HOLD shall be disabled, blocked, or rejected.
ABORT shall be disabled, blocked, or rejected.
COMPLETE shall remain available when allowed by approved workflow logic.
ARCHIVE shall be available only after the locked runtime batch has reached Complete status.
The system shall not change START, HOLD, or ABORT control-state tags for locked runtime batch instances. Equipment-conflict protection for START shall remain enforced. Completing or archiving a locked batch shall not overwrite, release, or otherwise affect equipment claims owned by another active runtime batch instance.

Archive Behavior
Archive shall be implemented as a GMP-retentive workflow action.
Archive shall not delete, overwrite, purge, or otherwise remove:
Saved batch setup records
Runtime batch records
Equipment claim history
Audit trail records
Historian data
Report records
Cached reporting data
Archive shall be available only for runtime batch instances that have reached Complete status. Runtime batch instances that are Loaded, Running, Held, or Aborted shall not be eligible for Archive unless an approved exception workflow is formally defined.
When a completed runtime batch instance is archived, the system shall hide the associated runtime batch card from the active batch overview. Archiving shall remove the card from the active operating view only; it shall not remove the underlying batch data or GMP-relevant records.
Archive shall release any active equipment claims associated with the archived runtime batch instance. Equipment associated with the archived runtime batch instance shall transition to RELEASED unless the equipment remains associated with another active runtime batch instance under approved workflow logic.
Released equipment shall become available for display and selection according to equipment enabled status and approved tag browser configuration.
Archive shall create an audit trail record in accordance with Section 11.
Archived runtime batch instances shall remain available for audit trail review and reporting according to applicable retention and access requirements. Reports shall continue to distinguish archived runtime batch instances using batch name, Run Instance, batch_run_uid, and/or Displayed Run Instance ID.







































































Reporting and Run Instance Identification
Batch reporting shall be based on the selected runtime batch instance, not solely on the saved batch name.
The same saved batch setup may be loaded and executed multiple times. Each loaded/runtime batch instance shall have a unique batch_run_uid and Displayed Run Instance ID. Reporting functions shall use these runtime identifiers to distinguish one execution from another.
The Reports screen shall provide sufficient runtime-identification information for users to select the correct report. At minimum, the report selection table shall include:
Batch Name
Run Instance and/or Displayed Run Instance ID
Batch Status
Applicable runtime timestamps, where available
The Batch Report first page shall display the selected runtime batch instance. At minimum, the first page shall include:
Batch Name
Run Instance and/or Displayed Run Instance ID
Where applicable, the Batch Report first page may also include:
Selected suite
Selected equipment
Start timestamp
Complete timestamp
Archive timestamp or archive status
Report generation timestamp
Cached reporting data stored in cache_batch_reporting_json or an equivalent approved schema object shall be associated with the specific runtime batch instance using batch_run_uid and/or Displayed Run Instance ID.
Report export permissions and report export audit requirements are defined in Section 11.

10.4.1 Report Selection Filtering
The Reports screen shall suppress report selection rows that do not represent a valid completed runtime batch interval.
At minimum, report selection shall exclude:
Records without a Batch End Time.
Records where Batch End Time equals Batch Start Time.
Records where Batch End Time is earlier than Batch Start Time.
Only records with batch_end_time > batch_start_time shall be displayed in the report selection table.
The visible Run Instance ID column shall be displayed as the final visible column in the report selection table, while preserving the underlying report-selection bindings required to generate the selected Batch Report.

Save Setup stores a new batch setup or updates an existing batch setup in SQL. Load Batch creates a new runtime batch instance/card from a saved batch setup. Both actions shall be controlled by security permissions and shall generate audit records.
Start, Hold, Abort, Complete, and Archive shall be secured runtime batch actions. Abort and Archive User-level permissions shall be confirmed by site policy. Archive shall be available only for completed batches, and Supervisor-only access is recommended unless otherwise approved.
Alarm setpoint changes shall remain restricted to Supervisor-level users. Report export shall be available only to authorized users and shall identify the selected runtime batch instance. Audit trail access shall be restricted to authorized users, with User or QA read-only access defined only if approved by site policy.
Equipment Tag Browser save functions shall be restricted to Supervisor users. Saving configuration changes shall require confirmation before changes are written to live Ignition tag configuration.

Audit Trail Requirements
Batch workflow actions shall generate audit trail records sufficient to reconstruct:

who performed the action;
what action was performed;
what runtime batch instance was affected;
what value or state changed;
whether the write succeeded; and
any applicable notes or system messages.
Audit trail records shall be generated for GMP-relevant batch setup, batch runtime workflow, equipment claim, archive, alarm setpoint, report export, and security-relevant actions.
At minimum, batch action audit records shall include the following data elements:
Audit Field
Requirement
User
Authenticated user identity associated with the action.
Session
Ignition Perspective session identifier or equivalent session/context identifier.
Action Name
Name of the action performed, such as Save Setup, Load Batch, Start, Hold, Abort, Complete, Archive, equipment claim transition, alarm setpoint change, report export, or rejected workflow action.
Action Value
Submitted value, command, selected control, status transition, report export option, alarm setpoint value, or other action-specific value.
Batch Path
Ignition project/tag path or logical batch path associated with the action, where applicable.
Batch ID / Batch Name
Saved batch identifier and displayed batch name associated with the action.
Run Instance / Hash
Runtime batch identifier, including batch_run_uid, Displayed Run Instance ID, run hash, or equivalent approved runtime identifier.
Previous Control State
Control state, batch status, equipment claim state, alarm setpoint value, or other relevant value before the action.
New Control State
Control state, batch status, equipment claim state, alarm setpoint value, or other relevant value after the action.
Write Result
Result of the applicable Ignition tag write, SQL write, report export request, or rejected/failed action.
Notes
Operator-entered notes, system messages, rejection reasons, exception details, or other action-specific context where applicable.
Timestamp
Date/time when the action occurred or was attempted.

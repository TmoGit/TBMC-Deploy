# Commission 06H.1 — Remote InfluxDB server readiness
Revision 01 | 27 November 2026 | Execute on DB server 10.1.0.132 only

## Objective and authority
Establish a persistent, privately reachable InfluxDB 2.x service and the production bucket `TBMC-Sensor-Data` with least-privilege credentials for Ignition/Kymera. Execute authorized changes, not merely recommendations. Create the production bucket if absent; reuse it if present. Preserve existing measurements, retention, credentials and consumers. Only the uniquely identified verification probe is authorized as a test write. Do not expose port 8086 publicly. Preserve successful configuration at completion.

## 1. Preflight and baseline
- Confirm host identity, interfaces, OS, service account, installed InfluxDB version (previously reported 2.8.0), executable, service wrapper, startup mode, actual command line/config/environment precedence, storage paths, disk space, clock/time zone and synchronization. Redact secrets. Confirm this is the intended server, not a substitute.
- Inspect listeners, /health, service logs, existing organization and bucket inventory, current firewall profiles/rules and approved private network route. Determine whether initialization is already complete; never rerun setup on an initialized instance. If uninitialized, initialize only with existing owner-approved organization/admin details via secure local input; if unavailable report blocker, do not invent credentials or organization.
- Capture protected service/config/firewall baseline and existing supported backup/recovery evidence before changes. Do not copy live database files as a substitute for a consistent backup. Keep sensitive originals local, not in Git or review ZIP.

## 2. Persistent network readiness
- Verify whether TCP 8086 is bound only to loopback. If necessary, configure the existing service using its actual supported persistent configuration mechanism to listen on the intended private interface (prefer 10.1.0.132; preserve authorized existing local consumers, using an all-interface bind only if necessary with verified restrictive firewall controls). Do not launch a second influxd process or create a duplicate service.
- Allow inbound TCP 8086 only from the authorized Ignition source (172.16.81.201 or documented/verified translated source address) via the approved private route/VPN. Check effective firewall policy including any broader existing rules; do not disable firewall or weaken unrelated rules. If routing/NAT/security group changes are required outside this host, document exact dependency rather than guessing or widening access.
- Use existing approved TLS configuration if present, verify certificate trust and name; do not bypass validation. If HTTP is the current design, verify that the path is approved private/protected transport before transmitting credentials. Otherwise stop token transfer until secure transport is available.
- Restart only the InfluxDB service if required, within an authorized window and after verifying no unacceptable impact to existing consumers. Verify automatic startup configuration, listener and health after the change. No reboot required. Confirm local health using actual endpoint and, where feasible, private-interface health; remote reachability is independently tested in 06H.2.

## 3. Bucket and credentials
- Identify actual organization name and ID. Create or reuse `TBMC-Sensor-Data` in the correct organization. For a new bucket use infinite retention (no automatic expiration) unless an approved project retention requirement specifies otherwise; record this default for owner review. Preserve existing retention if present; report conflicts without overwriting. Do not create a separate test bucket.
- Create a dedicated token `Ignition-TP-IGN01-Production` with read/write permissions limited to this bucket. If matching token already exists, reuse only if its scope and secure availability are established; otherwise create a distinguishable new token without revoking existing credentials. Grant only read/write access to TBMC-Sensor-Data; no all-access or other bucket permissions.
- Deliver token only through approved secret store or direct secure owner handoff. Never echo token, place it in CLI arguments, transcript, report, repository, ZIP, screenshots, or plaintext handoff file. If secure handoff is unavailable, report pending credential transfer; do not fabricate a token or expose it. Use supported secure API/CLI credential handling, redact logs.
- Using the scoped credential, perform a local API write to a unique measurement `commissioning_db_probe` with a unique run ID, timestamp and known numeric value, then query it back from the same bucket and verify exact value/timestamp. Verify scope from permission metadata; do not test by attempting writes to other buckets. Record sanitized HTTP status and query result. This is a DB-side probe, not proof of Ignition historization. After recording evidence, delete only the uniquely named probe measurement within its exact run time window using the supported deletion API, and verify removal; if safe selective deletion cannot be established, retain and document the clearly identified probe. Never delete existing measurements.

## 4. Handoff and evidence
Produce `TBMC-COM06H1-INFLUXDB-<timestamp>-Review.zip` with:
- execution summary, final PASS/PARTIAL/BLOCKED status and exact blockers;
- before/after service configuration and listener, firewall scope, version, health, time sync and sanitized logs;
- organization name/ID, bucket name/ID, retention, endpoint URL, TLS requirements and token description/permission scope (NO TOKEN);
- DB probe run ID, timestamp, query and results; rollback plan for changed settings only;
- `06H1_Handoff.json` containing nonsecret endpoint, org, bucket, token reference/transfer status, allowed source, probe results and remaining dependencies for 06H.2.

PASS requires persistent service configuration, local health, private listener, restricted ingress, correct bucket and scoped write/read probe; remote route remains pending until 06H.2. Do not claim full remote acceptance. If blocked, retain safe successful changes and report exact next action. Roll back only changes causing regression; never delete a bucket containing data or revoke credentials used by other consumers. Do not commit secrets or sensitive backups to public Git.
